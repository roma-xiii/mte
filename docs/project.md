## 1. Назначение проекта

MTE — многоконное настольное приложение для просмотра биржевых графиков и списков наблюдения. Технологии: Tauri v2, Rust, React, TypeScript и SQLite.

Окно Home служит точкой запуска. Пользователь может открыть произвольное количество окон Chart. В каждом таком окне находятся рабочая область графиков и Watchlist. Первые источники данных — Binance и Bybit: спотовые и деривативные инструменты, включая линейные и инверсные контракты. Архитектура допускает подключение новых источников без преждевременного введения универсальных абстракций.

MVP включает каталог инструментов, исторические и realtime-свечи, котировки, управление графиками, Watchlist и сохранение пользовательского состояния. Синтетические инструменты, агрегация свечей, управление позициями и выставление ордеров не входят в MVP.

## 2. Общие принципы

- Одна задача roadmap — одна небольшая проверяемая ответственность, подходящая для отдельного ревью, тестирования и коммита.
- Предпочитать явные зависимости и простые доменные модули абстракциям «на будущее».
- Не изменять согласованные контракты, семантику функциональности и схему хранения без обсуждения.
- Источник истины для сохраняемого состояния — Rust и SQLite; React поддерживает локальное представление этого состояния.
- Не размещать доменную оркестрацию в обработчиках Tauri Commands и компонентах отображения.
- Сопровождать новое поведение релевантными тестами.
- Не расширять объём задачи, не выполнять посторонний рефакторинг и не создавать коммит без явного разрешения.

## 3. Именование

В собственных именах проекта применяется **noun-first**: сначала предметная сущность, затем уточнение или действие. Примеры: `watchlistCreate`, `watchlistInstrumentListGet`, `documentConfigCurrent`, `keyParsed`, `errorValidation`.

- Для коллекций использовать `List`, а не множественное число: `instrumentList`, не `instruments`.
- Избегать сокращений в доменных именах: `InstrumentId`, `WatchlistInstrumentId`.
- Типы запросов к командам называть `Payload`, а не `Input`.
- В Rust использовать `snake_case` для функций и переменных; в TypeScript — `camelCase`, для типов — `PascalCase`.
- Имена файлов TypeScript — `kebab-case`; по необходимости использовать `index.ts` для реэкспорта.
- Не переименовывать внешние API и обязательные имена библиотек ради соблюдения внутренних правил.

## 4. Архитектура Rust

Основные слои backend:

- `commands` — тонкие точки входа Tauri: получение Payload, первичная проверка границы API, вызов Case, преобразование ошибки в публичный формат.
- `cases` — сценарии приложения: оркестрация, доменная валидация, границы транзакций, взаимодействие с Storage, Service и Provider.
- `services` — переиспользуемая доменная логика; вводятся при реальной необходимости.
- `storages` — работа с SQLite: SQL-запросы, преобразование строк и ошибки хранения.
- `providers` — адаптеры внешних бирж и источников данных: запросы, преобразование форматов и нормализация ошибок.
- `core` — общие доменные модели, типизированные идентификаторы, enum и базовые типы ошибок.

Case может напрямую использовать любые необходимые Storage и Service. Связь «один Case — один Service» не требуется. Данные из Storage передаются другим компонентам через Case. Не создавать универсальный реестр репозиториев или сервисов ради единообразия.

Зависимости передаются явно. Конкретные Case регистрируются по отдельности в управляемом `State` Tauri. Общая инфраструктура, включая SQLx pool и менеджеры, передаётся нужным компонентам. Для внутренних Storage предпочитать конкретные реализации; интеграционные тесты выполнять на временной SQLite.

## 5. Идентификаторы и публичные контракты

- Идентификаторы — типизированные Rust-обёртки над UUID: `WindowId(Uuid)`, `ChartId(Uuid)`, `WatchlistId(Uuid)`, `InstrumentId(Uuid)` и аналогичные.
- ID создаются в Case, сохраняются в SQLite как `TEXT`, передаются в TypeScript как строки.
- Для сериализуемых структур Rust использовать `serde(rename_all = "camelCase")`.
- Типы TypeScript генерировать из Rust через `specta` / `tauri-specta`; не дублировать сгенерированные модели вручную.
- Frontend API оформлять классами со статическими методами, например `WatchlistApi.create(payload)`.
- Публичная ошибка: `ApiError { code, message, details? }`; на frontend используется `ApiException`.
- Ошибки Storage: `NotFound`, `Conflict`, `Database`, `Serialization`.
- Ошибки Provider: `RateLimited` (с задержкой повтора, если известна), `Network`, `Unavailable`, `InvalidRequest`, `Unsupported`, `Unauthorized`, `Unexpected`. Исходный код и сообщение биржи сохраняются для диагностики.
- Обязательное получение сущности возвращает `NotFound`, если она отсутствует; получение списка возвращает пустую коллекцию; необязательные настройки могут возвращать `Option`.

## 6. SQLite и сохраняемое состояние

- SQLite хранит состояние окон, графиков, компоновки, выбора в Workspace, каталог инструментов, Watchlist и настройки приложения.
- Использовать SQLx и миграции при запуске. Ошибка миграции прерывает запуск приложения.
- Использовать общий SQLx pool и явные транзакции для атомарных изменений. Методы Storage должны поддерживать работу в необходимом контексте pool/transaction.
- SQL, преобразование строк и сериализация сохраняемых JSON-структур принадлежат Storage; доменные модели не зависят от SQL-представления.
- Использовать внешние ключи и ограничения уникальности. Доменная валидация находится в Case, целостность БД дополнительно обеспечивается SQL-ограничениями.
- Исторические свечи хранятся в оперативной памяти, не в SQLite.
- Автоматическое резервное копирование SQLite не входит в MVP.

## 7. Архитектура React

Допустимые слои frontend: `pages`, `widgets`, `features`, `layouts`, `providers`, `compositions`, `blocks`, `atoms`, `icons`.

- Основное место UI-логики — Feature. Feature может содержать собственный Provider и несколько Context.
- Компоненты получают состояние через Context своей Feature, без прямых подписок на Zustand.
- Zustand допустим внутри Feature Provider, но не используется напрямую в дочерних компонентах.
- Каждое окно Chart запускает отдельный экземпляр React-приложения с локальным состоянием окна.
- Статические API-классы инкапсулируют Tauri Commands; EventService инкапсулирует подписки на Tauri Events.
- Для одного события в одном React-окне создаётся один централизованный физический слушатель, который распределяет обновления потребителям.
- `ChartBlock` — тонкая обёртка над Lightweight Charts. Оркестрация и жизненный цикл рыночных данных находятся вне неё.
- Сохраняемые изменения обычно выполняются в порядке **успешная операция Rust → обновление React**. Для явно оптимистичных действий предусмотрены откат и обработка ошибки.
- При изменении инструмента, таймфрейма, списка или жизненного цикла компонента устаревшие асинхронные результаты отменяются либо игнорируются.

## 8. Границы подсистем рыночных данных

- Адаптеры группируются по бирже (`providers/binance`, `providers/bybit`) и ответственности: инструменты, история, потоки.
- Интерфейсы разделены: `InstrumentProvider`, `HistoryProvider`, `StreamProvider`; общего универсального интерфейса биржи нет.
- Биржевые идентификаторы, интервалы, лимиты, форматы WebSocket и удалённые ошибки преобразуются внутри Provider.
- Общие менеджеры отвечают за кеширование, очереди, дедупликацию, ограничения запросов, подписки и восстановление соединений, но не разбирают биржевые форматы сообщений.
- История и realtime — отдельные направления. Их алгоритмы и жизненный цикл описываются в контекстах соответствующих функциональных областей.
- В MVP используются только исходные свечи бирж, без синтеза или агрегации неподдерживаемых таймфреймов.

## 9. Commands, Events и жизненный цикл

- Command — операция запрос/ответ. Event — уведомление об асинхронном изменении для заинтересованных окон; локальные UI-действия не требуют глобальных событий.
- Успешная сохраняемая операция возвращает инициатору актуальные данные. Межоконные события об изменениях отправляются после успешного сохранения.
- При первоначальной загрузке учитывать гонку между подпиской на Event и получением снимка состояния; для состояния realtime-соединений используется версия снимка.
- Home — единственное окно запуска; окон Chart может быть сколько угодно.
- Явное закрытие Chart удаляет сохранённое состояние этого окна. Закрытие Home завершает приложение, сохраняя записи открытых Chart для восстановления.
- Общий shutdown отличается от закрытия отдельного окна: при завершении приложения обработчики закрытия Chart не удаляют сохранённые записи.
- Восстановление каждого Chart-окна независимо: ошибка одного не блокирует остальные.
- Rust использует общий `CancellationToken` для штатного завершения, закрывает очереди и потоки, ожидает управляемые задачи до пяти секунд, записывает незавершённые задачи в лог и закрывает пул БД.

## 10. Логирование и диагностика

- Использовать `tracing` и `tracing-subscriber`.
- В разработке писать в консоль, в production — в ежедневные файлы. При запуске удалять файлы логов старше семи дней.
- `DEBUG` spans — для команд и значимых операций Case; `INFO` — для важных событий жизненного цикла; `WARN`/`ERROR` — по серьёзности ошибок.
- Не записывать в логи секреты и учётные данные.
- Установить panic hook и отслеживать завершение фоновых задач через их handles. Автоматический перезапуск задач не вводить без отдельного требования.

## 11. Работа над задачами и проверки

Каждая задача roadmap имеет одну ответственность и проверяемый результат.

**До реализации:**

1. Прочитать задачу, применимые разделы общего контекста и контексты функциональности.
2. Изучить существующий код, определить затрагиваемые контракты и файлы.
3. Предложить план реализации и тестирования. До утверждения плана код не менять.

**Во время реализации:**

1. Соблюдать утверждённый объём задачи и сложившиеся паттерны проекта.
2. Добавить целевые unit- или integration-тесты.
3. Для поведения SQLite использовать временную настоящую БД с миграциями вместо моков Storage.
4. Запустить применимые форматирование, статические проверки, сборку и тесты. Явно перечислить, что выполнено и что не запускалось.

**После реализации:**

1. Кратко описать изменённые файлы, поведение и результаты проверок.
2. Предоставить diff для ревью.
3. Не создавать Git-коммит без разрешения пользователя.
4. Не переходить к следующей задаче автоматически.
