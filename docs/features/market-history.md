## 1. Назначение

Подсистема предоставляет исторические OHLCV-свечи графикам MTE. Она скрывает различия REST API бирж, повторно использует загруженные данные между окнами и графиками, ограничивает нагрузку на провайдеров и поддерживает дозагрузку диапазонов. История хранится только в оперативной памяти, без записи свечей в SQLite.

## 2. Границы ответственности

- **`ChartProvider` (React)** запрашивает первоначальную историю, догружает старые свечи при прокрутке и запрашивает восстановление пропущенного диапазона после разрыва realtime. Отменяет неактуальные запросы и не применяет устаревшие ответы.
- **`DataMarketHistoryApi` (TypeScript)** — типизированный интерфейс вызовов Rust-команд для истории.
- **Rust Command** принимает типизированный запрос, передаёт его соответствующему Case и возвращает нормализованные свечи либо `ApiError`.
- **Case** оркестрирует получение истории, проверяет доменные условия и обращается к `HistoryManager`.
- **`HistoryManager`** управляет RAM-кешем, покрытием диапазонов, очередью REST-запросов, приоритетами, дедупликацией, повторными попытками и отменой.
- **`HistoryProvider`** выполняет один REST-запрос к конкретной бирже на один допустимый диапазон и преобразует ответ в общую модель свечи. Адаптер объявляет ограничения API, в частности максимальное количество свечей на запрос и поддерживаемые таймфреймы.
- **Общий для биржи HTTP-клиент** обеспечивает транспорт, таймауты, заголовки и согласованное ограничение запросов с учётом биржевых лимитов.

`HistoryManager` не управляет WebSocket-подписками. `SubscriptionManager` не хранит исторический кеш.

## 3. Доменная модель и сериализация

### 3.1. Свеча

```rust
#[derive(Debug, Clone, Serialize, Deserialize, specta::Type)]
#[serde(rename_all = "camelCase")]
pub struct Candle {
    pub time: i64,
    pub open: f64,
    pub high: f64,
    pub low: f64,
    pub close: f64,
    pub volume: f64,
}
```

`time` — Unix seconds UTC, время открытия свечи. Остальные поля — конечные числа `f64` (без NaN и бесконечностей). Для пары `InstrumentId + Timeframe` ключ свечи — `time`. Возвращаемый список отсортирован по возрастанию `time`, без повторяющихся времён. Объём (`volume`) передаётся в нормализованном значении базового актива, если биржа предоставляет такое значение; преобразование выполняет адаптер. Свечи берутся из биржевого ответа, без синтетического заполнения интервалов.

### 3.2. Таймфрейм

```rust
pub enum Timeframe {
    Minute1, Minute3, Minute5, Minute15, Minute30,
    Hour1, Hour2, Hour4, Hour6, Hour12,
    Day1, Week1, Month1,
}
```

Стабильные значения сериализации (в том же порядке): `1m`, `3m`, `5m`, `15m`, `30m`, `1h`, `2h`, `4h`, `6h`, `12h`, `1d`, `1w`, `1M`. Регистр важен: `1m` — минута, `1M` — месяц. Использовать явные `serde(rename = "...")` для вариантов, а не `rename_all`; TypeScript-типы генерируются через `specta`. Поддержка интервалов зависит от провайдера и рынка, неподдерживаемый интервал даёт `Unsupported`. Месячный интервал определяется календарём UTC, а не фиксированным количеством секунд.

### 3.3. Варианты запроса

```rust
#[derive(Debug, Clone, Serialize, Deserialize, specta::Type)]
#[serde(tag = "type", rename_all = "camelCase")]
pub enum HistoryRange {
    Latest { count: u32 },
    Before { time: i64, count: u32 },
    Between { time_from: i64, time_to: i64 },
}

#[derive(Debug, Clone, Serialize, Deserialize, specta::Type)]
#[serde(rename_all = "camelCase")]
pub struct HistoryGetPayload {
    pub instrument_id: InstrumentId,
    pub timeframe: Timeframe,
    pub range: HistoryRange,
}
```

- `Latest { count }` — не более `count` последних доступных свечей.
- `Before { time, count }` — не более `count` свечей со временем открытия строго меньше `time`.
- `Between { timeFrom, timeTo }` — свечи с временем открытия в полуоткрытом диапазоне `[timeFrom, timeTo)`.
- `count` должен быть положительным; `timeFrom < timeTo`. Ошибочные параметры дают `InvalidRequest` на публичной границе.
- Если биржа вернула меньше свечей, чем запрошено, возвращается фактическое количество; пустой ответ — `[]`, а не ошибка. Дополнительные запросы только ради достижения `count` не выполняются. Интервалы без биржевых свечей не заполняются.

Пример сериализованного диапазона: `{ "type": "before", "time": 1795000000, "count": 100 }`. Для `Between` поля в JSON — `timeFrom`, `timeTo`.

## 4. Контракты компонентов

### 4.1. Tauri Command и Case

Единственная публичная команда получения истории — `history_candle_list_get`:

```rust
#[tauri::command]
async fn history_candle_list_get(
    payload: HistoryGetPayload,
    case: tauri::State<'_, HistoryGetCase>,
) -> Result<Vec<Candle>, ApiError>;
```

`HistoryGetCase` принимает `HistoryGetPayload`, проверяет корректность диапазона, находит инструмент через `InstrumentStorage`, проверяет доступность таймфрейма для его рынка и передаёт запрос `HistoryManager`. Успешный результат — `Vec<Candle>`; отдельный объект-обёртка для списка не требуется. Команда не содержит логики очереди, кеширования или биржевых преобразований.

Frontend: `DataMarketHistoryApi.candleListGet(payload: HistoryGetPayload): Promise<Candle[]>`. `ChartProvider` вызывает API при первой загрузке, прокрутке и восстановлении пропусков. Для фоновой предзагрузки приоритет определяется сценарием Rust, а не произвольным значением из публичного Payload.

### 4.2. HistoryProvider

```rust
pub struct HistoryProviderRequest {
    pub instrument: Instrument,
    pub timeframe: Timeframe,
    pub range: HistoryRange,
}

pub struct HistoryProviderCapabilities {
    pub timeframe_list: Vec<Timeframe>,
    pub candle_limit: u32,
}

// Логический контракт адаптера; конкретная async-сигнатура
// следует выбранному способу реализации trait в Rust.
fn capabilities(&self, market_type: MarketType) -> HistoryProviderCapabilities;
async fn candle_list_get(
    &self,
    request: HistoryProviderRequest,
) -> Result<Vec<Candle>, ProviderError>;
```

`HistoryProvider` выполняет **один** допустимый REST-запрос к Binance или Bybit. Он преобразует `Instrument` в нативный идентификатор рынка, `Timeframe` — в биржевой интервал, а ответ — в `Vec<Candle>`. Не управляет кешем, очередью, повторами или объединением нескольких REST-страниц. `candle_limit` — максимум свечей одного REST-запроса для соответствующего рынка. Нормализация обеспечивает сортировку и отсутствие дублей.

При `Between` адаптер передаёт границы с учётом включительности нативного API и отфильтровывает результат по `[timeFrom, timeTo)`. Неподдерживаемый интервал — `ProviderError::Unsupported`. Пустой корректный ответ — `Ok(vec![])`.

### 4.3. HistoryManager

```rust
pub enum HistoryPriority { High, Low }

pub struct HistoryManagerRequest {
    pub instrument: Instrument,
    pub timeframe: Timeframe,
    pub range: HistoryRange,
    pub priority: HistoryPriority,
}

async fn candle_list_get(
    &self,
    request: HistoryManagerRequest,
    cancellation: CancellationToken,
) -> Result<Vec<Candle>, HistoryError>;
```

`HistoryManager` получает уже найденный `Instrument`, выбирает соответствующий `HistoryProvider`, учитывает кеш и покрытие, разбивает запросы по `candle_limit`, ставит недостающие загрузки в очередь и объединяет результаты. Выход — только `Vec<Candle>`, по возрастанию времени, без дублей. Внутренние структуры очереди и кеша не являются публичными API.

`Latest` и `Before` задают ограничение по количеству, `Between` — временные границы. Менеджер не добирает свечи до заданного `count`, если корректный ответ биржи содержит меньше элементов. При разбиении больших запросов менеджер может выполнить несколько REST-запросов для покрытия явно запрошенного диапазона, но не делает дополнительные запросы ради искусственного достижения числа свечей.

### 4.4. Ошибки

- `ProviderError`: `RateLimited`, `Network`, `Unavailable`, `InvalidRequest`, `Unsupported`, `Unauthorized`, `Unexpected`. Сохранять исходные биржевые код и сообщение; для `RateLimited` — `retryAfter`, если известен.
- `HistoryError`: `InstrumentNotFound`, `InvalidRequest`, `Unsupported`, `Provider(ProviderError)`, `Cancelled`. Это ошибки оркестрации, а не новая иерархия биржевых ошибок.
- `HistoryGetCase` преобразует `HistoryError` и ошибки поиска инструмента в `ApiError { code, message, details? }`; `InstrumentNotFound` соответствует `NotFound`, неподдерживаемый таймфрейм — `Unsupported`, некорректный диапазон — `InvalidRequest`.
- Пустой или короткий корректный ответ провайдера не является ошибкой. Частично закешированные валидные свечи сохраняются после ошибки последующей загрузки; ошибку запрошенной операции не маскировать успешным пустым списком.

### 4.5. Отмена на границе React / Rust

Публичный `HistoryGetPayload` **не содержит** `CancellationToken`. `ChartProvider` при смене инструмента, таймфрейма или размонтировании помечает старое поколение запроса неактуальным и не применяет поздний ответ. Внутри Rust каждый потребитель `HistoryManager` имеет собственный `CancellationToken`; отмена одного ожидания не прерывает общую загрузку, пока она нужна другим. Когда потребителей не осталось, REST-запрос допускается отменить; уже полученные свечи остаются в кеше.

Обычный Tauri `invoke` сам по себе не гарантирует отмену уже выполняющегося Rust-запроса при игнорировании Promise в React. Поэтому для MVP игнорирование устаревшего ответа на стороне React **не считается физической отменой Rust-задачи**: такая задача может завершиться и наполнить общий кеш. Отдельную публичную команду отмены и реестр `requestId` не вводим. Независимая отмена Rust-потребителей применяется там, где жизненный цикл запроса управляется Rust. Это различие должно учитываться в тестах и реализации.

## 5. Кеш в оперативной памяти

Кеш глобален для процесса MTE и разделяется всеми Chart-окнами.

- Ключ: `InstrumentId + Timeframe`.
- Содержимое: упорядоченные свечи и сведения о покрытых временных диапазонах.
- Политика вытеснения: LRU.
- Целевой бюджет: **256 МБ**.
- Активно используемые данные защищены от вытеснения; при необходимости фактическое потребление может временно превысить бюджет.
- После завершения процесса кеш исчезает. SQLite не используется для хранения исторических свечей.

Информация о покрытии необходима, чтобы не принимать наличие нескольких свечей за гарантию полноты всего промежуточного диапазона.

## 6. Очередь REST-запросов

### Приоритеты

- **Высокий:** первоначальная загрузка графика и ручные запросы данных.
- **Низкий:** предварительная подгрузка и фоновое восстановление пробелов.

Высокоприоритетные запросы выбираются раньше низкоприоритетных. Внутри одного приоритета действует FIFO. Если к уже ожидающему низкоприоритетному запросу присоединяется высокоприоритетный потребитель, запрос повышается в приоритете.

### Параллелизм

Для каждого провайдера допускается до **трёх одновременно выполняемых REST-запросов**. Значение настраивается. Ограничения биржи, включая вес запросов, учитываются общим механизмом лимитирования HTTP-клиента.

### Повторные попытки

Для временных ошибок выполняются до **трёх повторов после первоначальной попытки** с экспоненциальной задержкой и jitter. При наличии `Retry-After` он учитывается. Постоянные ошибки не повторяются автоматически.

Типизированные ошибки провайдера включают `RateLimited` (с `retryAfter`, если известно), `Network`, `Unavailable`, `InvalidRequest`, `Unsupported`, `Unauthorized` и `Unexpected`.

## 7. Дедупликация и отмена

- Совпадающие запросы к одному инструменту, таймфрейму и диапазону используют одну незавершённую загрузку.
- Каждый потребитель может отменить ожидание независимо от остальных.
- Отмена одного потребителя не отменяет запрос, если его результат нужен другим.
- Когда потребителей больше нет, выполняющийся HTTP-запрос можно отменить.
- Уже полученные и валидные свечи остаются в кеше.

Смена инструмента или таймфрейма в React не должна приводить к применению ответа предыдущего запроса, даже если физическая отмена не успела завершиться.

## 8. Сценарии использования

### Первоначальная загрузка

При появлении графика `ChartProvider` запрашивает **500 последних свечей**. REST-загрузка и realtime-подписка запускаются параллельно. Пока история не получена, realtime-обновления буферизуются по времени открытия свечи; после получения REST они объединяются с историей и передаются в `ChartBlock`.

### Прокрутка в прошлое

При приближении к началу загруженного диапазона запрашиваются ещё **100 более старых свечей**. Кеш исключает повторное получение уже покрытых участков.

### Восстановление после разрыва WebSocket

После восстановления соединения график запрашивает недостающий временной диапазон, включая последнюю свечу перед разрывом для согласования границы. Полученная история объединяется с актуальными свечами без дублей, с сохранением пользовательского масштаба и положения графика.

### Переключение инструмента или таймфрейма

`ChartProvider` освобождает прежнее потребление истории, очищает отображение старого инструмента и начинает новый запрос. Ответы предыдущего поколения запроса игнорируются. Масштаб относится к конкретному `Chart` и не является глобальной настройкой инструмента или таймфрейма.

## 9. Согласование истории и realtime

Исторический REST-кеш и поток текущих свечей имеют разные жизненные циклы. `HistoryManager` хранит REST-историю; `ChartProvider` объединяет её с поступающими WebSocket-обновлениями.

- Первоначально буферизованные realtime-свечи заменяют REST-свечи с тем же временем открытия.
- После инициализации новые обновления текущей свечи передаются через `series.update()`.
- Свечи с временем открытия раньше последней отображаемой не передаются напрямую в `series.update()`; при необходимости выполняется синхронизация диапазона через историю.
- При первоначальной установке набора используется `setData()`, затем инкрементальные обновления.
- Realtime не инициирует REST-запрос на каждое закрытие свечи.

## 10. Ошибки и деградация

Ошибка загрузки истории показывается внутри затронутого графика с возможностью повтора. Остальные графики и окна продолжают работать. Частично закешированные валидные данные не удаляются из-за ошибки следующей загрузки.

Недоступность realtime не препятствует отображению полученной REST-истории. Состояние соединения и его индикация относятся к подсистеме Market Stream.

## 11. Тестирование

Проверяются как минимум:

- нормализация, сортировка и устранение дублей свечей;
- расчёт отсутствующих участков покрытия и разбиение по лимитам провайдера;
- повторное использование кеша и LRU-вытеснение с защитой активных данных;
- дедупликация одинаковых запросов и независимая отмена потребителей;
- приоритеты FIFO, повышение приоритета и лимит параллелизма;
- повторы временных ошибок, `Retry-After` и отсутствие повторов постоянных ошибок;
- загрузка 500 последних и подгрузка 100 предыдущих свечей;
- защита React от устаревших ответов;
- слияние REST и realtime на одной временной границе;
- восстановление пропусков после переподключения;
- локализация ошибки в одном графике.

## 12. Ограничения MVP

- Исторические свечи не сохраняются на диск.
- Синтетические свечи не создаются.
- Не вводится отдельное глобальное хранилище масштаба по `InstrumentId + Timeframe`.
- Подсистема истории не владеет WebSocket-соединениями и не управляет подписками.
