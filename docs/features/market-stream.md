# MTE — архитектурный контекст Market Stream

## 1. Назначение

Market Stream обеспечивает получение биржевых данных в реальном времени (свечи для графиков и котировки для Watchlist), повторное использование физических WebSocket-подписок, маршрутизацию сообщений потребителям и восстановление после разрывов соединения. Подсистема не отвечает за долговременное хранение истории: исторические свечи получает `HistoryManager`.

## 2. Границы и компоненты

- `SubscriptionManager` — единый backend-менеджер подписок, WebSocket-пулов, потребителей, переподключений и доставки данных.
- `StreamProvider` — биржевой адаптер протокола: адреса подключений, формат subscribe/unsubscribe, ACK, heartbeat, разбор сообщений и нормализация данных.
- `providers/binance/stream` и `providers/bybit/stream` — конкретные реализации адаптеров.
- `DataMarketStreamApi` — единая frontend-граница подписки на свечи и котировки.
- `ChartProvider` — жизненный цикл свечной подписки конкретного графика.
- `WatchlistFeature` — жизненный цикл подписок на котировки видимых элементов списка.
- `EventService` — единый физический listener на тип события в пределах frontend-окна.

`SubscriptionManager` работает с явной коллекцией адаптеров `StreamProvider` по `providerId`; глобальный универсальный реестр провайдеров не требуется. Адаптер одной биржи обслуживает поддерживаемые рынки Spot, Linear и Inverse, выбирая соответствующий endpoint и протокол.

## 3. Идентификаторы и ключи

- Инструмент идентифицируется `InstrumentId`, который разрешается в биржевые идентификаторы через каталог.
- Логический ключ свечного потока включает провайдера, рынок, инструмент, канал свечей и `Timeframe`.
- Логический ключ котировок включает провайдера, рынок, инструмент и канал котировок.
- Подписка потребителя содержит `subscriptionId`, `windowId` и `consumerId`.
- Одна логическая подписка может иметь несколько потребителей из разных окон и компонентов.

Менеджер дедуплицирует логические подписки: несколько потребителей одного ключа используют одну физическую биржевую подписку. `SessionId` в контракте MVP не используется. `SubscriptionId`, `ConsumerId`, `WindowId` и `InstrumentId` — отдельные типизированные идентификаторы; `SubscriptionId` и `ConsumerId` представлены UUID, `WindowId` использует общую модель подсистемы Window. При регистрации повторного сочетания `windowId + consumerId + instrumentId + channel` возвращается прежний `subscriptionId`.

### 3.1. Доменные типы и сериализация

Контракты Rust экспортируются в TypeScript через общие bindings (`serde`/`specta`); поля в IPC и событиях — `camelCase`. Названия вариантов перечислений сериализуются явно и не зависят от Rust-имен.

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
#[serde(tag = "type", rename_all = "camelCase")]
pub enum StreamChannel {
    Ticker,
    Candle { timeframe: Timeframe },
}

pub struct Ticker {
    pub instrument_id: InstrumentId,
    pub price: f64,
    pub price_change_percent_24h: Option<f64>,
    pub volume_24h: Option<f64>,
    pub time: i64,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[serde(rename_all = "camelCase")]
pub enum StreamConnectionStatusType {
    Connecting,
    Connected,
    Reconnecting,
    Disconnected,
}

pub struct StreamConnectionStatus {
    pub provider_id: ProviderId,
    pub market_type: MarketType,
    pub status: StreamConnectionStatusType,
    pub version: u64,
}
```

`StreamChannel` сериализуется как `{ "type": "ticker" }` либо `{ "type": "candle", "timeframe": "1h" }`. `Timeframe` использует enum из Market History. Realtime-свеча — та же модель `Candle` (`time`, `open`, `high`, `low`, `close`, `volume`), время — Unix seconds UTC. У `Ticker` поле `time` — Unix seconds UTC; неизвестные 24-часовые показатели передаются как `null`, а не заменяются нулём. Значения `f64` должны быть конечными; невалидные биржевые сообщения не распространяются как рыночные события.

### 3.2. Контракты регистрации потребителей

```rust
pub struct StreamSubscribePayload {
    pub instrument_id: InstrumentId,
    pub channel: StreamChannel,
    pub window_id: WindowId,
    pub consumer_id: ConsumerId,
}

pub struct StreamSubscribeResult {
    pub subscription_id: SubscriptionId,
}

pub struct StreamUnsubscribePayload {
    pub subscription_id: SubscriptionId,
}
```

`SubscriptionId` обозначает регистрацию потребителя, а не физическую подписку на бирже. Один потребитель может иметь несколько регистраций на разные инструменты или каналы. При повторной регистрации того же сочетания полей возвращается существующий идентификатор; при смене инструмента или канала прежняя регистрация освобождается отдельно. `windowId` проверяется backend по контексту вызывающего Tauri-окна: переданное значение не может разрешать регистрацию за другое окно.


## 4. Контракт StreamProvider

Адаптер отвечает за особенности конкретной биржи:

- выбор WebSocket endpoint по рынку;
- построение сообщений подписки и отписки;
- разбор подтверждений (ACK), ошибок и служебных сообщений;
- heartbeat/ping-pong в соответствии с протоколом;
- нормализацию свечей и котировок в общие модели MTE;
- предоставление ограничений биржи, в том числе максимального числа подписок на соединение;
- преобразование биржевых ошибок в `ProviderError` с сохранением исходных кода и сообщения.

Адаптер не управляет множеством потребителей, не решает, кому отправлять события, и не хранит состояние React-окон. Эти обязанности принадлежат `SubscriptionManager`.

### 4.1. Типизированная граница StreamProvider

`StreamProvider` получает разрешённые через каталог биржевые данные инструмента и `StreamChannel`, а возвращает нормализованные сообщения протокола. Публичная граница адаптера включает операции:

- `connection_endpoint_get(market_type: MarketType) -> Result<StreamEndpoint, ProviderError>` — выбор адреса и протокола соединения;
- `subscription_limit_get(market_type: MarketType) -> StreamSubscriptionLimit` — ограничения количества потоков на соединение;
- `subscribe_message_list_get(channel_list: &[StreamProviderChannel]) -> Result<Vec<StreamProviderMessage>, ProviderError>` — подготовка сообщений подписки;
- `unsubscribe_message_list_get(channel_list: &[StreamProviderChannel]) -> Result<Vec<StreamProviderMessage>, ProviderError>` — подготовка сообщений отписки;
- `message_parse(message: StreamProviderMessage) -> Result<StreamProviderEvent, ProviderError>` — разбор входящего сообщения в ACK, ошибку, heartbeat или нормализованное рыночное событие.

`StreamProviderChannel` содержит `instrument: Instrument` и `channel: StreamChannel`; биржевые `symbol`/`externalId` берутся из `Instrument`, а не из React. `StreamProviderEvent` — типизированное объединение подтверждения подписки, ошибки протокола, служебного сообщения, `Ticker` и `Candle` с ключом исходного потока. Транспорт WebSocket и распределение физических соединений остаются в `SubscriptionManager`. Конкретные wire-типы `StreamEndpoint`/`StreamProviderMessage` не являются IPC-контрактами и определяются реализацией адаптера.

### 4.2. Cases, Commands и SubscriptionManager

| Tauri Command | Case | Payload | Результат |
|---|---|---|---|
| `stream_subscribe` | `StreamSubscribeCase` | `StreamSubscribePayload` | `StreamSubscribeResult` |
| `stream_unsubscribe` | `StreamUnsubscribeCase` | `StreamUnsubscribePayload` | `()` |
| `stream_connection_status_list_get` | `StreamConnectionStatusListGetCase` | Без аргументов | `Vec<StreamConnectionStatus>` |

Cases выполняют валидацию, разрешение инструмента из каталога и обращаются к `SubscriptionManager`. Commands не создают WebSocket-соединения и не содержат бизнес-логику. Публичный frontend-класс `DataMarketStreamApi` предоставляет одноимённые типизированные методы и подписку на события через `EventService`.

Основные операции `SubscriptionManager`:

```rust
async fn subscribe(
    &self,
    payload: StreamSubscribePayload,
) -> Result<StreamSubscribeResult, StreamError>;

async fn unsubscribe(
    &self,
    payload: StreamUnsubscribePayload,
) -> Result<(), StreamError>;

async fn connection_status_list_get(&self) -> Vec<StreamConnectionStatus>;

async fn window_release(&self, window_id: WindowId) -> Result<(), StreamError>;
```

`window_release` — внутренний вызов Rust при закрытии окна; отдельной Tauri Command для него нет. Отписка удаляет ровно одну регистрацию; повторная отписка уже освобождённого `subscriptionId` безопасна и не затрагивает других потребителей. Если при отписке или закрытии окна ещё есть потребители того же логического ключа, физический поток сохраняется. Последний потребитель запускает уже установленный 30-секундный период простоя.

## 5. Подписка и отписка

1. Frontend-потребитель обращается к `DataMarketStreamApi`.
2. Backend регистрирует потребителя по логическому ключу и возвращает идентификатор подписки.
3. Если физическая подписка уже существует, новый биржевой subscribe не отправляется.
4. Если подписка новая, `SubscriptionManager` выбирает соединение с учётом лимитов адаптера и отправляет subscribe.
5. При отписке удаляется только конкретный потребитель. Пока остаются другие потребители, физическая подписка сохраняется.
6. После исчезновения последнего потребителя применяется 30-секундный период простоя перед физической отпиской.

Подписки и отписки могут объединяться в пакеты в пределах возможностей биржевого протокола. Менеджер распределяет подписки между несколькими WebSocket-соединениями при достижении лимита одного соединения.

## 6. Подключение и восстановление

`SubscriptionManager` управляет состоянием WebSocket-пулов, повторными подключениями и подтверждением подписок. После восстановления соединения он повторно отправляет все актуальные подписки на этом соединении. `StreamProvider` предоставляет протокольные операции, но не принимает решения о перечне восстанавливаемых подписок.

Восстановление потока не гарантирует доставку всех сообщений, пропущенных во время разрыва. Для графиков пропущенный диапазон восстанавливается через `HistoryManager`, включая последнюю свечу перед разрывом. Временное мерцание статуса переподключения допустимо.

## 7. Доставка событий

Менеджер маршрутизирует нормализованные события только тем frontend-окнам, в которых зарегистрированы соответствующие потребители. В одном окне `EventService` поддерживает один физический listener на тип события и распределяет сообщения подписчикам внутри React.

Для свечей используются нормализованные значения времени открытия в Unix seconds UTC и OHLCV (`f64`). Для котировок используется единая нормализованная модель, не зависящая от формата биржевого сообщения.

Frontend не должен открывать самостоятельные WebSocket-соединения с биржами в обход backend-менеджера.

### 7.1. Контракты Tauri Events

События отправляются адресно в окна, где зарегистрированы потребители, а не широковещательно во все окна приложения.

| Событие | Payload |
|---|---|
| `stream_ticker_updated` | `StreamTickerUpdatedPayload` |
| `stream_candle_updated` | `StreamCandleUpdatedPayload` |
| `stream_connection_status_changed` | `StreamConnectionStatus` |

```ts
interface StreamTickerUpdatedPayload {
  subscriptionId: SubscriptionId;
  ticker: Ticker;
}

interface StreamCandleUpdatedPayload {
  subscriptionId: SubscriptionId;
  candle: Candle;
}

interface StreamConnectionStatus {
  providerId: ProviderId;
  marketType: MarketType;
  status: StreamConnectionStatusType;
  version: number;
}
```

Один входящий биржевой тик или обновление свечи маршрутизируется каждому активному `subscriptionId` соответствующего логического потока в заинтересованных окнах. Внутри окна `EventService` сохраняет один физический listener на тип события. После отписки сообщения прежнего `subscriptionId` игнорируются frontend, даже если они были поставлены в очередь ранее.

События состояния соединения содержат версию соответствующего `providerId + marketType`; снимок `stream_connection_status_list_get` содержит те же поля и версии. Frontend применяет только состояние с версией не меньше уже известной для данного сочетания, чтобы снимок не откатывал более новое событие. Изменение статуса соединения не создаёт автоматически исторические свечи: восстановление диапазона инициирует `ChartProvider` через Market History.

## 8. Состояние соединений

Состояния: `Connecting`, `Connected`, `Reconnecting`, `Disconnected`.

Статус ведётся по сочетанию провайдера и рынка. Изменения передаются событиями; также доступен command для получения текущего снимка статусов. Снимок и события используют монотонную версию, чтобы frontend мог избежать гонки при начальной подписке на события и запросе состояния.

В Chart-окне показывается один индикатор предупреждения, если недоступно хотя бы одно соединение, используемое данным окном. По нажатию открываются подробности состояния.

## 9. Интеграция с ChartProvider

- `ChartProvider` запускает загрузку REST-истории и подписку на свечи параллельно.
- Пока история загружается, realtime-сообщения буферизуются с сохранением последнего обновления для каждого времени открытия свечи.
- После загрузки REST-истории буфер объединяется с историей, при совпадении времени открытия приоритет имеет буфер realtime.
- Первичная установка данных выполняется через `dataSet()`, дальнейшие последовательные обновления — через `update()`.
- Обновления на frontend объединяются по кадрам через `requestAnimationFrame`.
- При смене инструмента или таймфрейма предыдущий поток освобождается, прежние данные очищаются, устаревшие ответы и события игнорируются.
- После переподключения `ChartProvider` инициирует восстановление пропущенных свечей через `HistoryManager`, сохраняя пользовательский масштаб и положение графика там, где это применимо.
- Сообщение со временем открытия раньше последней отображаемой свечи не передаётся напрямую в `series.update()`; при необходимости выполняется синхронизация истории.

Масштаб принадлежит конкретному `Chart`; он не синхронизируется между окнами или другими графиками.

## 10. Интеграция с Watchlist

- Watchlist использует котировочные подписки через `DataMarketStreamApi`.
- При сворачивании Watchlist подписки освобождаются, при разворачивании создаются заново.
- При переключении списка состав подписок изменяется по разнице необходимых инструментов.
- Компоненты получают данные через API/контексты `WatchlistFeature`, а не обращаются напрямую к backend-событиям или Zustand.
- Отдельный глобальный frontend-кеш последних цен в рамках MVP не вводится; менеджер может поддерживать последний тикер для обслуживания подписчиков.

## 11. Ошибки и завершение работы

Ошибки внешнего провайдера нормализуются в `ProviderError`: `RateLimited`, `Network`, `Unavailable`, `InvalidRequest`, `Unsupported`, `Unauthorized`, `Unexpected`. Неожиданный сбой одного соединения не должен останавливать другие соединения или графики.

`StreamError` различает некорректный запрос (`InvalidRequest`), отсутствующий инструмент (`NotFound`), неподдерживаемый канал (`Unsupported`), ошибку провайдера (`Provider`) и внутреннюю ошибку (`Internal`). Commands преобразуют ошибки в общий `ApiError { code, message, details? }`; исходные код и сообщение биржи сохраняются в деталях, когда они доступны. Ошибка регистрации возвращается вызывающему потребителю; ошибка уже работающего соединения отражается в статусе и обрабатывается механизмом восстановления. Отдельного события с полным биржевым исключением не вводится.

При закрытии Chart-окна освобождаются его потребители. При общем завершении приложения используется общий `CancellationToken`: менеджер прекращает новые операции, завершает соединения и фоновые задачи в пределах установленного лимита ожидания. Неуспешные завершения логируются.

## 12. Проверки и тестирование

Реализация должна покрывать следующие сценарии:

1. Два потребителя одного ключа создают одну физическую подписку.
2. Отписка одного потребителя не прекращает поток для другого.
3. После последней отписки физическая подписка освобождается по истечении 30 секунд, если потребитель не вернулся.
4. Подписки распределяются по соединениям с учётом лимитов адаптера.
5. После разрыва выполняются переподключение и повторная отправка актуальных подписок.
6. Подтверждения подписки и ошибки протокола корректно обрабатываются.
7. События доставляются только окнам с зарегистрированными потребителями.
8. Начальная загрузка REST и realtime не приводит к потере более свежего обновления текущей свечи.
9. Устаревшие события после переключения инструмента или таймфрейма не попадают в график.
10. Снимок статусов и события не приводят к откату к устаревшей версии.
11. Сворачивание Watchlist освобождает его котировочные подписки.
12. Закрытие окна и завершение приложения корректно освобождают ресурсы.
13. Повторная регистрация одного `windowId + consumerId + instrumentId + channel` возвращает прежний `subscriptionId`.
14. Регистрация с чужим `windowId` отклоняется.
15. События содержат `subscriptionId`, не доставляются посторонним окнам и не применяются после отписки.
16. Сериализация `StreamChannel`, `StreamConnectionStatusType` и Payload совпадает с TypeScript bindings.

## 13. За пределами подсистемы

- Долговременное хранение свечей на диске.
- Расчёт синтетических свечей.
- Управление расположением графиков и сохранение их настроек.
- Управление составом и порядком Watchlist.
- Самостоятельная реализация биржевых WebSocket-соединений на frontend.

Эти обязанности принадлежат другим подсистемам MTE либо не входят в MVP.
