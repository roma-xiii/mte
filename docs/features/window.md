## 1. Назначение и границы

MTE использует Tauri v2 и поддерживает одно окно **Home** и произвольное число окон **Chart**.

- **Home** — единственное окно запуска новых Chart-окон. Закрытие Home завершает приложение.
- **Chart** — независимое физическое окно, в котором React загружает собственный Chart Workspace и Watchlist. Окно может содержать несколько графиков.
- Явно закрытое пользователем Chart-окно удаляется из сохраняемого состояния и не восстанавливается.
- При завершении приложения открытые Chart-окна остаются в SQLite и восстанавливаются при следующем запуске.
- Будущие типы окон (например, Positions или API Keys) не реализуются в MVP.

Подсистема Window отвечает за физические окна, их идентичность, геометрию и жизненный цикл. Она не управляет свечами, подписками, состоянием отдельных графиков или операциями Watchlist.

## 2. Доменная модель

### AppWindow

```ts
interface AppWindow {
  id: WindowId;
  subsystem: WindowSubsystem;
  x: number;
  y: number;
  width: number;
  height: number;
  maximized: boolean;
}
```

- `WindowId` — типизированный UUID, генерируется в Rust Case, хранится в SQLite как TEXT, в TypeScript представлен строкой.
- `WindowSubsystem` различает тип окна. В MVP сохраняются и восстанавливаются Chart-окна; Home — singleton приложения.
- Геометрия выражена в **логических пикселях (DIP)**, координаты и размеры — `f64` в Rust.
- Для максимизированного окна сохраняются последние границы в обычном состоянии, чтобы корректно восстановить размер после выхода из максимизации.

Связанные сущности `Chart`, `ChartLayout` и `ChartWorkspaceState` описываются в контексте Chart Workspace. Для нового Chart-окна они создаются вместе с записью `AppWindow`.

## 3. Хранение

SQLite — источник истины для списка Chart-окон, которые требуется восстановить.

- Таблица `app_window` хранит `AppWindow`.
- `chart`, `chart_layout`, `chart_workspace_state` связаны с `app_window` внешними ключами; при удалении окна связанные записи удаляются через `ON DELETE CASCADE`.
- Схема создаётся и изменяется через SQLx migrations.
- Создание окна и его начального Workspace в базе выполняется **одной транзакцией**.
- Удаление записи окна и связанных сущностей выполняется атомарно в базе.
- Хранение состояния окон не зависит от доступности бирж или каталога инструментов.

### AppWindowStorage

Типизированный контракт (запись в таблицу выполняется в `Storage`; ID создаёт `Case`):

```rust
pub struct WindowGeometry {
    pub x: f64,
    pub y: f64,
    pub width: f64,
    pub height: f64,
    pub maximized: bool,
}

impl AppWindowStorage {
    pub async fn create(&self, window: &AppWindow) -> Result<(), StorageError>;
    pub async fn get(&self, window_id: WindowId) -> Result<AppWindow, StorageError>;
    pub async fn list(&self) -> Result<Vec<AppWindow>, StorageError>;
    pub async fn geometry_set(
        &self,
        window_id: WindowId,
        geometry: &WindowGeometry,
    ) -> Result<(), StorageError>;
    pub async fn delete(&self, window_id: WindowId) -> Result<(), StorageError>;
}
```

Сигнатуры выше определяют аргументы и возвращаемые значения. Для вызовов в общей транзакции Storage предоставляет соответствующие операции с переданным SQLx executor; создание `AppWindow` вместе с первоначальным Workspace выполняется через один executor транзакции.

- `get` возвращает `StorageError::NotFound`, если запись отсутствует.
- `list` возвращает пустой `Vec`, если сохранённых окон нет; Home в список не входит.
- `geometry_set` и `delete` возвращают `StorageError::NotFound`, если окно отсутствует.
- Ошибки ограничений SQLite и SQLx преобразуются в принятые варианты `StorageError`.

Соглашения по `StorageError`, SQLx, транзакциям и именованию определены в [project.md](../project.md).

## 4. Контракты Cases и публичного API

### Доменный тип и перечисление

```rust
pub struct AppWindow {
    pub id: WindowId,
    pub subsystem: WindowSubsystem,
    pub x: f64,
    pub y: f64,
    pub width: f64,
    pub height: f64,
    pub maximized: bool,
}

pub enum WindowSubsystem {
    Home,
    Chart,
}
```

`WindowId` — типизированный UUID. Rust-модели передаются в TypeScript через генерируемые `specta`-контракты, с `camelCase` для JSON-полей. `WindowGeometry` содержит только геометрию, без идентификатора.

### Внутренние Cases

| Case | Аргументы `execute` | Успешный результат | Ошибки |
|---|---|---|---|
| `WindowChartCreateCase` | Нет | `AppWindow` | Ошибка транзакции или создания физического окна |
| `WindowRestoreCase` | Нет | `()` | Ошибка получения списка окон; ошибки отдельных окон обрабатываются внутри Case |
| `WindowCloseCase` | `WindowId` | `()` | Ошибка удаления записи или закрытия физического окна |
| `WindowGeometrySetCase` | `WindowId`, `WindowGeometry` | `()` | Ошибка валидации геометрии или SQLite |

Внешний результат Case выражается через `Result<…, ApiError>`; внутренние ошибки Storage преобразуются в согласованный API-контракт на границе Case/Command. Для восстановления ошибка отдельного окна логируется, а запись сохраняется для следующего запуска.

### Публичная Tauri-команда

| Command | Payload | Успешный ответ |
|---|---|---|
| `window_chart_create` | Нет | `AppWindow` |

`window_chart_create` вызывает `WindowChartCreateCase`. `AppWindow` возвращается только после успешного создания физического окна. Ошибка передаётся через `ApiError`.

**Отдельной публичной команды `window_close` нет.** `WindowCloseCase` вызывается внутренним обработчиком нативного запроса закрытия Chart-окна. `WindowRestoreCase` запускается из Rust при старте приложения. `WindowGeometrySetCase` вызывается из Rust после обработки нативных событий и debounce.

### События

Для управления окнами не вводится отдельный пользовательский Tauri Event. Перемещение, изменение размеров, максимизация и запрос закрытия обрабатываются как нативные события Tauri в Rust. React получает `WindowId` из контекста своего физического окна и загружает Workspace независимо.

## 5. Создание Chart-окна

Оркестрация: `WindowChartCreateCase`.

1. Определить `WindowId` и `ChartId`.
2. Выбрать Watchlist с минимальным `createdAt`, если он существует.
3. Для выбранного Watchlist определить первый инструмент в его порядке; если список пуст или отсутствует, выбранный инструмент равен `null`. Другие Watchlist не просматриваются.
4. В одной SQLite-транзакции создать `AppWindow`, первый `Chart`, `ChartLayout` и `ChartWorkspaceState`.
5. Начальный таймфрейм первого Chart — **1d (D1)**. В новом окне один график.
6. Зафиксировать транзакцию.
7. Создать физическое Chart-окно средствами Tauri.
8. Если создание физического окна завершилось ошибкой, выполнить компенсирующее удаление сохранённого состояния созданного окна и вернуть ошибку.

После создания физического окна его React-приложение самостоятельно загружает состояние Workspace через соответствующий Case. Создание окна не должно ожидать сетевых запросов, обновления Instrument Catalog или загрузки свечей.

## 6. Восстановление при запуске

Оркестрация: `WindowRestoreCase`.

1. Инициализировать SQLite и выполнить миграции до начала восстановления.
2. Получить из SQLite список Chart-окон, оставшихся открытыми на момент завершения предыдущего запуска.
3. Для каждой записи создать физическое Tauri-окно с сохранённой геометрией и состоянием максимизации.
4. Если конфигурация мониторов изменилась, скорректировать положение и размер, чтобы окно было доступно пользователю.
5. Ошибка восстановления одного окна логируется и не препятствует восстановлению остальных.
6. Запись окна, которое не удалось восстановить, остаётся в SQLite для следующей попытки при последующем запуске.
7. React внутри каждого восстановленного окна отдельно загружает Workspace.

Окна отображаются без ожидания обновления каталога инструментов или доступности бирж. Сохранённый инструмент может быть показан по локальным данным SQLite.

## 7. Изменение геометрии

- Источник событий — нативные события перемещения, изменения размеров и максимизации Tauri.
- Обработчики передают изменения в Rust; запись в SQLite выполняется с **debounce**, чтобы не создавать запись при каждом событии перемещения.
- В максимизированном состоянии не перезаписывать последние обычные границы размерами развёрнутого окна.
- При восстановлении учитывать доступные мониторы и ограничивать геометрию видимой областью.
- Принудительная синхронная запись последнего ожидающего debounce при закрытии не требуется. Допускается потеря самого последнего изменения геометрии.

## 8. Закрытие отдельного Chart-окна

Оркестрация: `WindowCloseCase`.

1. Перехватить запрос закрытия физического Chart-окна, чтобы оно не закрылось раньше завершения операции.
2. Удалить `AppWindow` из SQLite; связанные записи Workspace удаляются каскадно.
3. При ошибке базы **не закрывать окно** и сообщить об ошибке.
4. После успешного удаления закрыть физическое окно Tauri.
5. Если физическое закрытие не удалось, записать ошибку в лог и предпринять повторную попытку; удалённую запись SQLite не восстанавливать.

Освобождение React-подписок и прочих ресурсов окна выполняется в рамках жизненного цикла соответствующих функциональных подсистем и общего механизма управления подписками.

## 9. Завершение всего приложения

Закрытие Home означает завершение MTE, **а не пользовательское закрытие каждого Chart-окна**.

- Перед общим завершением приложение устанавливает глобальное состояние `ShuttingDown`.
- Обработчики закрытия Chart-окон во время `ShuttingDown` **не вызывают** `WindowCloseCase` и не удаляют записи окон.
- Открытые Chart-окна остаются в SQLite для восстановления.
- Общий механизм shutdown отменяет фоновые задачи, закрывает соединения и очереди, ожидает завершения в пределах установленного лимита и закрывает пул SQLite. Подробные общие правила — в [project.md](../project.md).

Это разграничение обязательно также для последовательности системных событий закрытия окон, которые Tauri может отправлять при завершении приложения.

## 10. Граница с Chart Workspace

`WindowChartCreateCase` создаёт первоначальные записи Workspace, но не реализует операции изменения графиков.

- Внутри одного Chart-окна графики используют общий выбранный инструмент.
- Каждый `Chart` имеет собственные настройки масштаба; окно не является владельцем масштаба.
- Добавление графиков, смена таймфрейма, изменение layout, переключение инструментов и сохранение настроек конкретного Chart относятся к `Chart Workspace`.
- Восстановление физического окна и получение его рабочего состояния — отдельные операции.

## 11. Ошибки и наблюдаемость

- Ошибки SQLite преобразуются в принятый `StorageError`, а публичные команды возвращают согласованный `ApiError`.
- Неудачное создание физического окна после успешного сохранения требует компенсирующего удаления.
- Ошибки восстановления отдельных окон не останавливают весь запуск приложения.
- Ошибки закрытия и восстановления логируются через `tracing` с идентификатором окна и контекстом операции.
- Нельзя логировать секреты и чувствительные данные.

## 12. Проверки и тестирование

Тесты следует распределять по небольшим задачам реализации, а не создавать одним крупным этапом.

- Создание окна сохраняет полный набор связанных записей атомарно.
- Ошибка внутри транзакции создания не оставляет частичного Workspace.
- Ошибка создания физического окна запускает компенсирующее удаление.
- Явное закрытие удаляет окно и связанные записи; ошибка удаления не закрывает физическое окно.
- Завершение MTE сохраняет открытые Chart-окна для восстановления.
- Ошибка восстановления одного окна не блокирует другие.
- Восстановление не зависит от сети и обновления каталога.
- Геометрия корректно сохраняется и восстанавливается, в том числе при максимизации и изменении набора мониторов.
- Для SQLx использовать тестовую SQLite-базу с реальными миграциями согласно общим соглашениям проекта.

## 13. Вне ответственности подсистемы

- Хранение и загрузка исторических свечей.
- WebSocket-подписки и котировки.
- CRUD Watchlist и инструменты в списках наблюдения.
- Редактирование ChartLayout и параметров графиков после создания окна.
- Окна других подсистем, не входящие в MVP.
