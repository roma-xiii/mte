## 1. Назначение и границы

Instrument Catalog — единый локальный справочник доступных инструментов Binance и Bybit. Он используется при поиске и выборе инструмента, восстановлении сохранённого состояния окон и Watchlist, а также при маршрутизации запросов истории и realtime к нужному провайдеру.

Каталог хранится в SQLite. Frontend не загружает весь каталог в память: поиск и выборка выполняются через Rust Cases и Storage. Отсутствие сети или незавершённое обновление не блокируют запуск MTE и работу с ранее сохранёнными записями.

В MVP поддерживаются биржевые рынки Spot, Linear и Inverse; модель допускает Option и дальнейшее расширение источников. Синтетические инструменты и генерация синтетических свечей не входят в MVP.

## 2. Типизированные контракты моделей и перечислений

Основные типы Rust являются источником истины; TypeScript-типы генерируются через `specta`, а Tauri-сериализация использует `camelCase`. UUID-идентификаторы передаются строками. Значения перечислений хранятся в SQLite стабильными строковыми кодами `snake_case` (для приведённых однословных вариантов они совпадают с `camelCase`).

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, Type)]
#[serde(rename_all = "camelCase")]
pub enum MarketType { Spot, Linear, Inverse, Option }

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, Type)]
#[serde(rename_all = "camelCase")]
pub enum ContractType { Perpetual, Dated }

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, Type)]
#[serde(rename_all = "camelCase")]
pub enum InstrumentStatus {
    Active, Suspended, Prelaunch, Delisted, Unavailable, Unknown,
}

pub struct Instrument {
    pub id: InstrumentId,
    pub provider_id: ProviderId,
    pub external_id: Option<String>,
    pub market_type: MarketType,
    pub contract_type: Option<ContractType>,
    pub symbol: String,
    pub base_asset: String,
    pub quote_asset: String,
    pub status: InstrumentStatus,
    pub metadata: serde_json::Value,
}
```

| Перечисление | Вариант | Семантика |
|---|---|---|
| `MarketType` | `Spot` | Спотовый рынок |
| | `Linear` | Дериватив с линейным расчётом |
| | `Inverse` | Дериватив с обратным расчётом |
| | `Option` | Опционный рынок; предусмотрен моделью, не входит в MVP |
| `ContractType` | `Perpetual` | Бессрочный контракт |
| | `Dated` | Контракт с датой экспирации |
| `InstrumentStatus` | `Active` | Торговля доступна |
| | `Suspended` | Торговля временно приостановлена |
| | `Prelaunch` | Торги ещё не начались |
| | `Delisted` | Биржа сообщает о снятии инструмента с торгов |
| | `Unavailable` | Инструмент отсутствует в последнем полном успешном снимке своего сегмента |
| | `Unknown` | Статус источника не сопоставлен с известным статусом MTE |

`Spot` всегда имеет `contract_type = None`; для поддерживаемых фьючерсных рынков `Linear` и `Inverse` контракт имеет `Perpetual` или `Dated`. Для `Option` в MVP не фиксируется контрактный тип. `Unavailable` назначается только механизмом синхронизации, а не провайдером. Неизвестный биржевой статус нормализуется в `Unknown` с сохранением исходного значения в `metadata`; неизвестный тип рынка не подменяется другим типом и приводит к ошибке нормализации.

## 3. Контракты запросов, результатов и Cases

```rust
pub struct InstrumentGetPayload {
    pub instrument_id: InstrumentId,
}

pub struct InstrumentListGetPayload {
    pub instrument_id_list: Vec<InstrumentId>,
}

pub struct InstrumentSearchPayload {
    pub query: String,
    pub provider_id: Option<ProviderId>,
    pub market_type: Option<MarketType>,
    pub status: Option<InstrumentStatus>,
}

pub struct InstrumentRefreshPayload {
    pub provider_id: ProviderId,
    pub market_type: MarketType,
}
```

| Case | Вход | Успешный результат | Ошибки |
|---|---|---|---|
| `InstrumentGetCase` | `InstrumentGetPayload` | `Instrument` | `NotFound`, ошибки SQLite/сериализации |
| `InstrumentListGetCase` | `InstrumentListGetPayload` | `Vec<Instrument>` | Ошибки SQLite/сериализации |
| `InstrumentSearchCase` | `InstrumentSearchPayload` | `Vec<Instrument>` | Ошибки SQLite/сериализации |
| `InstrumentRefreshCase` | `InstrumentRefreshPayload` | `()` | `ProviderError`, ошибки SQLite/сериализации |

`InstrumentListGetCase` возвращает только существующие записи в порядке их ID во входном списке. Отсутствующие ID пропускаются без ошибки; повторяющиеся входные ID не требуют повторного элемента результата. Пустой вход возвращает пустой список. `InstrumentGetCase` для отсутствующего ID возвращает `NotFound`.

`InstrumentSearchCase` ищет по `symbol`, `baseAsset`, `quoteAsset` через SQLite `LIKE`, с фильтрами по одному провайдеру, рынку и статусу. Отсутствующий `status` означает `Active`. Пустая строка запроса допускается. Максимум 50 результатов, стабильная сортировка. Debounce 250 мс выполняется на frontend.

## 4. Контракт InstrumentProvider

```rust
pub struct InstrumentProviderItem {
    pub external_id: Option<String>,
    pub market_type: MarketType,
    pub contract_type: Option<ContractType>,
    pub symbol: String,
    pub base_asset: String,
    pub quote_asset: String,
    pub status: InstrumentStatus,
    pub metadata: serde_json::Value,
}

pub trait InstrumentProvider {
    async fn instrument_list_get(
        &self,
        market_type: MarketType,
    ) -> Result<Vec<InstrumentProviderItem>, ProviderError>;
}
```

`ProviderId` задаётся конкретным адаптером/его регистрацией, а не дублируется в каждом элементе. В `InstrumentProviderItem` отсутствует внутренний `InstrumentId`: он создаётся Case при обнаружении новой записи. Успешный результат содержит **полный** снимок запрошенного сегмента, в том числе может быть пустым; частичная загрузка должна завершаться ошибкой. Провайдер не сохраняет данные в SQLite и не устанавливает `Unavailable`.

## 5. Контракты InstrumentStorage

| Метод | Вход | Успешный результат |
|---|---|---|
| `get` | `InstrumentId` | `Instrument`, иначе `StorageError::NotFound` |
| `list_get` | `Vec<InstrumentId>` | `Vec<Instrument>` по правилам пакетного чтения |
| `search` | `InstrumentSearchPayload` | `Vec<Instrument>` (не более 50) |
| `snapshot_apply` | `ProviderId`, `MarketType`, полный нормализованный список `Instrument` | `()` |

`InstrumentRefreshCase` сопоставляет записи по стабильному биржевому ключу, сохраняет существующие UUID и создаёт новые. `snapshot_apply` выполняется в транзакции, помечает отсутствующие записи **только своего сегмента** как `Unavailable` и не удаляет записи, на которые ссылаются другие подсистемы. Граница транзакции охватывает изменение снимка и запись времени успешного обновления в `AppSettingsStorage`. Для нескольких Storage используется общий SQLx executor. Ошибки Storage: `NotFound`, `Conflict`, `Database`, `Serialization`.

## 6. Публичные Tauri Commands и событие

| Command | Payload | Результат |
|---|---|---|
| `instrument_get` | `InstrumentGetPayload` | `Instrument` |
| `instrument_list_get` | `InstrumentListGetPayload` | `Instrument[]` |
| `instrument_search` | `InstrumentSearchPayload` | `Instrument[]` |

`InstrumentRefreshCase` не имеет публичной команды: запускается при старте и по расписанию внутри Rust. Commands тонкие, используют Case из Tauri State и преобразуют ошибки в `ApiError { code, message, details? }`.

```ts
interface InstrumentCatalogRefreshCompletedPayload {
  providerId: ProviderId;
  marketType: MarketType;
}
```

Событие `InstrumentCatalogRefreshCompleted` отправляется **один раз после успешного коммита конкретного сегмента**. При ошибке и откате не отправляется. Событие не содержит каталог; React повторяет активный поиск и пакетно перечитывает нужные модели `Instrument`.

## 7. Доменная модель

Основная сущность — `Instrument`:

```rust
struct Instrument {
    id: InstrumentId,
    provider_id: ProviderId,
    external_id: Option<String>,
    market_type: MarketType,
    contract_type: Option<ContractType>,
    symbol: String,
    base_asset: String,
    quote_asset: String,
    status: InstrumentStatus,
    metadata: serde_json::Value,
}
```

`InstrumentId` — типизированная UUID-обёртка, создаваемая в Case. Она стабильна при повторных обновлениях инструмента. `ProviderId` идентифицирует источник данных; `externalId` содержит биржевой идентификатор, когда он доступен. `MarketType` различает Spot, Linear, Inverse и Option. `ContractType` различает Perpetual и Dated, когда применимо.

`InstrumentStatus`: `Active`, `Suspended`, `Prelaunch`, `Delisted`, `Unavailable`, `Unknown`.

`Unavailable` означает, что запись отсутствует в последнем **полном и успешно обработанном** снимке каталога соответствующего источника/рынка. Это не статус сетевого соединения и не признак отсутствия котировки. Оригинальные значения биржи, не укладывающиеся в общую модель, могут сохраняться в `metadata`.

## 8. Идентичность и обновление записей

- Существующий инструмент сохраняет `InstrumentId` при синхронизации.
- Для сопоставления используется надёжный стабильный `externalId`, если провайдер его предоставляет; иначе применяется составной биржевой ключ с учётом `providerId`, `marketType`, `symbol` и типа контракта.
- Изменение `symbol` не трактуется автоматически как переименование без достоверного стабильного идентификатора.
- Новый инструмент получает новый `InstrumentId`.
- Ссылки из Watchlist и сохранённого Workspace используют внутренний `InstrumentId`, а не строковый `symbol`.

## 9. Разделение ответственности

```text
Tauri Command → InstrumentGetCase / InstrumentListGetCase / InstrumentSearchCase
                                         ↓
                                 InstrumentStorage → SQLite

Startup / Scheduler → InstrumentRefreshCase
                           ├── InstrumentProvider (Binance / Bybit)
                           ├── InstrumentStorage → SQLite
                           └── AppSettingsStorage → SQLite
                                         ↓
                        InstrumentCatalogRefreshCompleted Event
```

- **Commands**: тонкая точка входа, проверка формы входных данных, вызов Case и преобразование ошибки в `ApiError`.
- **Cases**: сценарии получения, поиска и обновления; доменные проверки, управление порядком операций и границами синхронизации.
- **InstrumentStorage**: SQL-чтение, поиск, атомарная запись снимка и сопоставление записей по согласованным ключам.
- **InstrumentProvider**: получение полного биржевого каталога и нормализация биржевых ответов в общие модели.
- **AppSettingsStorage**: хранение времени последнего успешного обновления отдельно для каждого сегмента `ProviderId + MarketType`.
- **Scheduler**: инициирование фонового обновления; не содержит бизнес-логики.

Отдельный `InstrumentCatalogService` не вводится: оркестрация остаётся в Case. Если общая повторно используемая логика действительно появится, её можно выделить в Service отдельным согласованным изменением.

## 10. Биржевые адаптеры

Адаптеры организуются по источнику и роли:

```text
providers/
  binance/
    instrument/
    history/
    stream/
  bybit/
    instrument/
    history/
    stream/
```

Роль каталога реализует `InstrumentProvider`. Один адаптер биржи маршрутизирует запросы по поддерживаемым категориям рынка. Внутри адаптера остаются биржевые endpoint, параметры запросов, коды статусов, преобразование идентификаторов и нормализация ошибок. Остальные слои работают с общими `Instrument` и `ProviderError`.

Для биржи используется общий HTTP-клиент с настройками таймаутов и соблюдением ограничений запросов. Ошибки провайдера представляются общими вариантами `RateLimited`, `Network`, `Unavailable`, `InvalidRequest`, `Unsupported`, `Unauthorized`, `Unexpected`; оригинальный код и сообщение биржи сохраняются для диагностики.

## 11. Обновление каталога

Обновление запускается в фоне при старте MTE, если каталог сегмента `ProviderId + MarketType` пуст либо после последнего успешного обновления прошло более 24 часов. Далее выполняется периодическая проверка и обновление примерно раз в час. Время последнего успешного обновления хранится в типизированных настройках приложения. Каждый сегмент `ProviderId + MarketType` обновляется независимо; одновременно выполняется не более одного обновления одного сегмента.

Последовательность:

1. Case запрашивает у адаптера полный список инструментов одного сегмента `ProviderId + MarketType`.
2. Адаптер нормализует ответ и сообщает о полноте полученного снимка.
3. Case допускает синхронизацию только при корректно полученном и нормализованном полном снимке соответствующей области.
4. Storage в одной транзакции добавляет новые записи, обновляет существующие с сохранением ID и переводит отсутствующие в полном снимке записи в `Unavailable`.
5. В той же транзакции сохраняется время последнего успешного обновления сегмента. После успешного коммита отправляется `InstrumentCatalogRefreshCompleted` с `providerId` и `marketType`.

Если ответ сегмента неполный или нормализация не удалась, отсутствующие инструменты **не** переводятся в `Unavailable`. Прежний каталог сохраняется; ошибка логируется. Неудача одного сегмента не блокирует остальные сегменты того же или другого провайдера. Сетевые ошибки не препятствуют работе UI с SQLite.

## 12. SQLite и транзакционность

Таблица `instrument` хранит внутренний ID, данные провайдера, тип рынка, символ, базовый и котируемый активы, статус и дополнительные метаданные. Уникальность биржевого ключа обеспечивается на уровне БД в соответствии с правилом идентичности.

`InstrumentStorage` поддерживает получение по `InstrumentId`, пакетное получение по списку ID, поиск с фильтрами и атомарную синхронизацию каталога. При синхронизации нельзя делать промежуточные изменения видимыми: либо весь корректный снимок применён, либо остаётся прежнее состояние. Для операций, включающих несколько Storage, Case передаёт общий транзакционный executor.

Сохранённые ссылки на инструмент не удаляются автоматически, когда его статус становится `Unavailable` или `Delisted`.

## 13. Поиск и выборка

Поиск выполняется непосредственно в SQLite, без FTS и без предварительной полной загрузки каталога в React.

- Поисковые поля: `symbol`, `baseAsset`, `quoteAsset`.
- Сопоставление: `LIKE` без учёта регистра в рамках возможностей SQLite; результаты имеют стабильный порядок.
- По умолчанию показываются инструменты со статусом `Active`.
- Результат ограничен первыми 50 записями; пустой запрос также возвращает первые 50.
- В интерфейсе поиск выполняется с debounce около 250 мс.
- UI предоставляет клавиатурную навигацию по найденным инструментам.
- `InstrumentListGetCase` позволяет получить модели по набору `InstrumentId` для Watchlist и восстановления состояния без индивидуального запроса на каждый элемент.

Внутренние параметры поиска позволяют ограничивать источник, категорию рынка и статус. Результат поиска содержит нормализованные модели инструментов.

## 14. Связь с UI и событиями

При открытии окна приложение не ждёт сети и не ждёт обновления каталога. Сохранённые инструменты читаются из SQLite. Если каталог пуст, UI показывает соответствующее пустое состояние; автоматический выбор первого появившегося после обновления инструмента не выполняется.

После успешного обновления сегмента Rust отправляет `InstrumentCatalogRefreshCompleted` с идентификатором провайдера и типом рынка. Открытый диалог поиска при получении события повторяет текущий запрос. Событие не передаёт весь каталог и не заменяет запрос к SQLite.

Выбор инструмента и его синхронизация между графиками одного Chart-окна относятся к [chart-workspace.md](./chart-workspace.md), а не к Instrument Catalog.

## 15. Ошибки и устойчивость

- Неудачная синхронизация не уничтожает сохранённые записи и не помечает отсутствующие как `Unavailable`.
- Ошибка SQLite откатывает транзакцию.
- Отсутствующий инструмент при обязательном `get` возвращает `StorageError::NotFound` с последующим отображением через согласованный `ApiError`.
- Неизвестный или неподдерживаемый биржевой тип не должен незаметно преобразовываться в неверный тип рынка.
- Оригинальная диагностическая информация биржи доступна в логах без секретов.
- Состояния `Suspended`, `Delisted` и `Unavailable` сохраняются и доступны для корректного отображения ранее выбранных инструментов.

## 16. Проверки и тестирование

Минимальный набор проверяемых сценариев:

1. Новые инструменты создаются с UUID и затем читаются из SQLite.
2. Повторная синхронизация сохраняет `InstrumentId` существующих записей.
3. Полный успешный снимок переводит отсутствующие записи в `Unavailable`.
4. Неполный/ошибочный снимок не меняет статусы отсутствующих инструментов.
5. Ошибка в середине SQL-транзакции не оставляет частично применённого каталога.
6. Ошибка Binance не блокирует обновление Bybit.
7. Одновременные запросы обновления одного провайдера не запускают дублирующую синхронизацию.
8. Поиск корректно ограничивает результат 50 записями, учитывает статус и ищет по предусмотренным полям.
9. Пакетное получение по ID возвращает доступные записи без полной загрузки каталога.
10. Событие завершения возникает после успешной фиксации обновления, а не до неё.

Интеграционные тесты Storage используют временную SQLite с настоящими миграциями. Провайдеры тестируются на нормализацию биржевых ответов и обработку ошибок. Общие требования к тестам и именованию определены в [project.md](../project.md).

## 17. За пределами функциональности

Instrument Catalog не управляет историческими свечами, WebSocket-подписками, Watchlist, раскладкой графиков и пользовательскими масштабами. Он предоставляет стабильную модель инструмента и возможность его найти или получить по ID. История и потоки используют `InstrumentId` и нормализованные сведения каталога, но реализуются в отдельных подсистемах.
