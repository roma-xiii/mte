# Задание opencode: инструкция запуска тестера

Выполнять после завершения и проверки сборки и состояния подключения из `.opencode/stage-1/README.md`. Если они ещё не готовы, сообщи об этом; не описывай запланированное поведение как существующее.

Работай из корня mte. Это задание разрешает редактирование документации в указанной области. Не делай commit/push и не меняй чужие изменения.

## Цель

Создать краткую воспроизводимую инструкцию запуска текущего тестера Nautilus + Tauri на машине разработчика.

## Область

Изменяй только корневые `INSTRUCTIONS.md`, `README.md` и `client-tauri/README.md`. Подробную инструкцию держи в INSTRUCTIONS.md, в README — краткое назначение проекта и ссылки без копирования всей инструкции.
Исходники, Makefile, manifest/lock-файлы, данные и содержимое mutations-bot не менять. Не устанавливай зависимости и не запускай серверы/GUI ради написания документации.

## Что проверить чтением

- nautilus/Makefile, pyproject.toml и main в websocket_server.py;
- client-tauri/package.json, vite.config.ts, src-tauri/tauri.conf.json;
- адрес подключения и поведение reconnect в Rust bridge;
- итоговый UI подключения и сообщения об ошибках.

## Что должно быть в инструкции

1. Требования по локальным manifest-файлам: Python, uv, Node/npm, Rust и инструменты сборки Tauri для macOS. Не выдумывай точные версии, если проект их не фиксирует.
2. Установка Python-зависимостей через существующий make install и frontend через npm ci. Ясно указать рабочие каталоги. Не использовать ошибочные абсолютные пути /nautilus и /client-tauri.
3. Два терминала: backend `make run`, desktop `npm run tauri dev`. Команды копируются от корня репозитория. Python пока запускается отдельно.
4. Порты 8765 (WS /ws) и 1420 (Vite). Если Rust использует фиксированный адрес, объяснить, что изменение только Python-порта разорвёт подключение.
5. Как открыть окно тестера, что ожидать при отсутствии backend и после его запуска. Отличить npm run dev от desktop: браузер сам по себе не предоставляет Tauri API.
6. Проверки `npm run build` и `cargo check --offline` с правильными каталогами. Уточнить, что offline-check требует уже имеющихся Rust-зависимостей; не выдавать его за установку с нуля.
7. Короткий сценарий технической проверки на сохранённом CSV, только по актуальному коду и известным проверкам. Указать, что правильность PnL и управления сессией будет доводиться следующими этапами. Не обещать готовые фьючерсы, восстановление теста или исправленную статистику раньше реализации.
8. Корректное завершение запущенных процессов и объяснение занятых портов без советов убивать все процессы Python/Node.

Не описывай исследования стратегий, старый mutations-bot или будущую упаковку Python внутрь приложения. Не добавляй несуществующий /health.

## Приёмка и отчёт

Проверь все упомянутые команды, пути и ссылки по текущим файлам. Отделяй сверку с кодом от фактического выполнения; не заявляй успешный запуск, если его не выполнял.
В отчёте: изменённые документы, найденные противоречия старой инструкции, что проверено чтением и что требует ручной проверки Codex.
