# Рабочий тестер Nautilus: аудит и план

Дата: 2026-09-17. Требования: `.opencode/tester.md`.

## Границы работы

Целевая связка: Python / Litestar / NautilusTrader → WebSocket → Tauri / Rust → React / Mantine / lightweight-charts.
`mutations-bot` — старая реализация, сохранённая ради стратегий. Не изменять, не интегрировать и не исследовать стратегии в рамках этого этапа.
SMA в `nautilus/strategies/` используется как технический пример для проверки ордеров и отображения; разработка торговой логики не входит в задачу.

## Что уже есть и чего не хватает

| Требование | Состояние по коду и проверкам |
|---|---|
| Биржа, пара с поиском, таймфрейм, диапазон | Биржа и таймфрейм выбираются; пара вводится текстом, каталога инструментов нет. Есть даты и число баров, валидация недостаточна. |
| Загрузка котировок и выбор сохранённых | Есть CCXT, CSV и менеджер файлов. Имена не учитывают биржу/рынок/диапазон, возможна перезапись другого набора. |
| Выбор стратегии и параметры | Реестр и динамическая форма есть, обнаружена одна SMA. |
| 1 бар/с при старте, до 100 бар/с | UI показывает 1, backend начинает с 0. Ожидание команды добавляет 0,1 с на бар и ограничивает скорость. |
| Pause / Resume / Stop | Команды есть. Нет события возобновления для UI; остановка связана с завершением транспорта. Требуется переделка жизненного цикла. |
| Свечи, входы/выходы, TP/SL | Свечи есть. Время входов передаётся в наносекундах, UI разбирает его как дату. Выходы не передаются в график. TP/SL представлены одноточечными сериями, открытые позиции не удаляются при закрытии. |
| Лог и сделки под графиком | Вкладки есть, сейчас справа. Полный лог при восстановлении не обеспечен: snapshot отдаёт последние 1000 записей. |
| Закрытие/открытие окна без потери теста | Rust хранит только полученный snapshot, но не обновляет его текущими событиями. Пересоздание окна не запрашивает актуальный снимок Python. |
| Независимость сессии от соединения | Не обеспечена: stop-флаг общий у WS и прогона; новое подключение получает свои очереди без подписки на события активного прогона. |
| Завершённый результат | После окончания Python удаляет текущую сессию; восстановление результата не работает. Статистика не согласуется с балансом. |

## Что проверено запуском

- Установлены локальные `.venv`, `node_modules`, Rust-зависимости; NautilusTrader версии 1.230.0.
- `cargo check --offline` в `client-tauri/src-tauri` — успешно.
- `npm run build` — этап TypeScript проходит, Vite падает: `index.html` ссылается на отсутствующий `/src/main.tsx`. Для многооконного приложения нужны корректные HTML entrypoints production-сборки.
- Python-сервер запущен на отдельном проверочном порту 18765, WebSocket отдаёт одну стратегию и три CSV.
- Реальный WS-прогон `BTCUSDT-1d.csv`, 73 бара, `trade_size=1`, `speed=100`: завершён за 9,05 с; получены 73 события bar, 1 entry, 1 position_opened, 0 trade.
- Начальный баланс 1 000 000; баланс последнего bar — 979 899,3419. При этом complete сообщает PnL=0 и total_trades=0. Это не проверенный финансовый результат.
- Переподключение после завершения начинается со strategies_list, snapshot отсутствует.
- Полный GUI-сценарий Tauri и загрузка данных с бирж пока не проверены. Успешная компиляция Rust не означает исправность UI.

Дополнительные причины по коду:

- В `websocket_server.py` PnL читается по ключу USD, хотя BTCUSDT использует USDT. Сделки извлекаются опросом состояния позиции после бара: так можно пропустить закрытие и разворот внутри обработки бара. После `engine.end()` финальные события повторно не собираются.
- В SMA параметр «Trade Size (USD)» используется как количество базового актива. В ветке TP/SL используется неимпортированный `OrderType`; одного исправления импорта недостаточно без проверки исполнения bracket-ордеров.
- Загрузчик делит символ после третьего знака: это не подходит, например, для DOGEUSDT. Инструменты создаются как универсальные CurrencyPair с фиксированными комиссиями и точностью, без явного рынка spot/perpetual.
- Ошибки загрузки CSV и настройки движка могут возникнуть до основного try/finally и не превратиться в корректное терминальное состояние сессии.
- delete_data не ограничивает разрешённый путь каталогом данных; проверка должна быть на сервере.

## Как запускать текущую версию

Два терминала, backend запускается отдельно — Rust сейчас не управляет Python-процессом.

```bash
cd /Users/hesoyam/Documents/home/projects/mte/nautilus
make run
```

```bash
cd /Users/hesoyam/Documents/home/projects/mte/client-tauri
npm run tauri dev
```

При отсутствии зависимостей: `make install` в `nautilus`, `npm ci` в `client-tauri`.
Рабочий адрес bridge фиксирован: `ws://127.0.0.1:8765/ws`; проверочный порт 18765 для обычного UI не подходит.
Обычный `npm run dev` открывает веб-часть, но не предоставляет Tauri invoke/events.

Для первого ручного прогона: открыть Backtest, выбрать Use saved data → BTCUSDT-1d.csv, SMA, Trade Size = 1, market, TP/SL = 0. Сейчас размер означает 1 BTC, несмотря на подпись USD. Эти параметры нужны только для воспроизведения технической проверки.
До исправления отчёта не оценивать по нему результаты стратегии. TF в заголовке CSV-прогона сейчас может не совпадать с файлом: UI передаёт прежний timeframe, хотя загрузчик берёт его из имени CSV.

## Согласованные решения

1. Первая версия — фьючерсы USDT perpetual Bybit/Binance. Спот пока не реализуем, но сохраняем возможность его добавить: явный тип рынка в конфигурации и метаданных, отдельное создание инструмента и настройка исполнения. Не подменять фьючерсы универсальной CurrencyPair и не зашивать perpetual во все слои.
2. Закрытие окна тестера не прерывает прогон; повторное открытие восстанавливает сессию. Продолжение после полного выхода из Tauri не является обязательным требованием первой версии. Это не означает, что разрыв WebSocket должен останавливать Python-сессию.
3. При Stop и естественном конце истории закрываем открытые позиции. Отменяем оставшиеся заявки, закрываем по последней доступной цене с учётом комиссии; только после обработки финальных исполнений формируем результат. Не обрабатываем будущие свечи ради закрытия. Stop во время паузы подчиняется той же политике.

Предлагаемый предел первой версии: один активный прогон; результат и история сохраняются до явного нового запуска. Перезапуск Python и архив нескольких прогонов — отдельный следующий этап, если не требуется иначе.

## Порядок доработки и приёмка

### 1. Воспроизводимый запуск

Исправить Vite entrypoints, закрепить инструкции и проверку запуска; показать состояние соединения в UI. Ошибки подключения и запуска должны быть видны пользователю.

Приёмка: `npm run build`, `cargo check --offline`; запуск двух процессов; открытие окна; получение списков CSV и стратегий; понятная ошибка при недоступном backend.

### 2. Сессия и управление — основной фундамент

Ввести серверный SessionManager, независимый от WS-подключений. Разделить stop-флаг прогона и отключение клиента. Состояния: idle / loading / running / paused / stopped / completed / failed. У сессии run_id, у событий последовательный seq; команды подтверждаются сервером. Новый запуск не должен смешивать события старого прогона.

Снимок содержит config, статус, скорость, прогресс, свечи, позиции, сделки, результат. Логи отдавать полностью, при необходимости страницами. Подписка на последующие события должна исключать пропуски и дубли между snapshot и live-потоком. Завершённую сессию сохранять. Начальная скорость — 1 бар/с, ожидание команд не должно ограничивать максимальную скорость.

Приёмка: start → pause → resume → stop → новый start; естественное завершение → новый start; ошибка → новый start. Закрыть/открыть окно во время running, paused и после завершения — восстановлены все данные и статус. Проверить потерю WS отдельно. Сравнить скорость 1/10/100 на короткой фиксированной истории, учитывая накладные расходы.

### 3. Корректные события исполнения и результат

Использовать события ордеров/исполнений/позиций Nautilus вместо определения сделок только опросом cache после бара. Нормализовать время и сторону сделки; определить единицы объёма. Получать PnL в валюте счёта, разделить balance/equity/realized/unrealized PnL/fees. Реализовать согласованную политику Stop и конца данных. Проверить market/limit/TP/SL на технических фикстурах, не менять торговые правила стратегий.

Приёмка: маленькие детерминированные наборы с ожидаемой ценой входа/выхода, комиссией и итоговым балансом; long/short, разворот, TP, SL, отклонение ордера, конец истории с позицией, Stop во время running и paused. После остановки/завершения нет открытых позиций и активных заявок, закрытие и комиссия отражены в сделках и отчёте. Отчёт, журнал и состояние счёта согласованы. Одинаковый результат при разных скоростях и паузах.

### 4. Данные и инструменты

Каталог пар с поиском для USDT perpetual Bybit/Binance. Тип рынка задаётся явно, чтобы позже добавить спот без изменения формата сессий и данных. Данные идентифицируются биржей, рынком, символом, TF и диапазоном; сохраняются CSV и метаданные. Загружать страницы без повторов, проверять UTC, порядок, дубликаты, пропуски и незакрытую последнюю свечу. Ограничить пути файлов и валидировать параметры сервером. Для CSV брать инструмент и TF из метаданных.

Приёмка: BTCUSDT и символ с базовым активом длиннее трёх знаков; диапазон дат и число баров; повторная загрузка; сбой сети; пустой/повреждённый CSV; два набора с одинаковой парой с разных бирж не перезаписывают друг друга. Тесты пагинации работают без биржи на фиксированных ответах.

### 5. Завершение интерфейса по требованиям

Входы и выходы на графике с единым форматом времени; настоящие линии TP/SL с обновлением и удалением. Вкладки лог/сделки разместить под графиком. Прогресс и кнопки отражают подтверждённое серверное состояние. Восстанавливать график из snapshot; пакетно обновлять UI на большой скорости, сохранять пользовательский масштаб.

Приёмка: визуальный прогон всех сценариев этапов 2–4 в Tauri; повторное открытие окна; корректные маркеры, линии и история; отсутствие заметного накопления задержки на 100 бар/с.

## Разделение работы с opencode

Codex: контракт событий, жизненный цикл сессии, интеграция Nautilus, модель исполнения, сверка результатов и сквозная приёмка.
Opencode: ограниченные задачи с заданными файлами, контрактом и проверкой. Выдавать последовательно; не поручать одновременно менять общий протокол или один и тот же файл.

| Задача для opencode | Зависимость и критерий |
|---|---|
| Исправить многостраничную Vite-сборку | Можно первой. Все существующие окна имеют HTML в dist, `npm run build` успешен; не менять backend. |
| Привести форму данных к утверждённому контракту | После этапа 4/фиксации API. Поиск пары, проверка дат/числа баров, метаданные CSV, осмысленные ошибки. |
| Обновить вкладки лог/сделки и их расположение | После фиксации типов. Под графиком, длинные логи не ломают layout, UI не теряет полную историю. |
| Нормализовать отображение времени и маркеры | После фиксации формата событий. Проверка на готовых фикстурах входа/выхода, без изменения Python. |
| Тесты валидации CSV и пагинации | После согласования интерфейсов загрузчика. Дубликаты, пропуски, пустые ответы, разные длины символов; без сетевых запросов. |

Формат задания: цель → разрешённые файлы → готовые типы/пример входа-выхода → критерии приёмки → команда проверки. После выполнения Codex проверяет diff и интеграцию. Исполнитель не должен маскировать ошибки нулями, заглушками и подавлением исключений.

## Готовность первой версии

Можно выбрать/загрузить данные, запустить пример стратегии, управлять скоростью и паузой, остановить или дождаться завершения, закрыть/открыть окно и получить актуальную сессию. Свечи, сделки, лог, TP/SL и результат согласованы. Повторный запуск работает без перезапуска приложения. Сборки и детерминированные проверки проходят.
