# Этап 2. Контракт серверной сессии

Статус: спецификация к реализации, не описание текущего API. Основа — `.opencode/tester.md` и согласованные решения в `.opencode/TESTER_PLAN.md`.

## Границы

Один активный прогон на Python-процесс. Клиенты наблюдают одну сессию; закрытие окна или WebSocket не останавливает движок. Завершённая сессия хранится в памяти до принятия следующего Start. Перезапуск Python теряет сессию; сохранение на диск и архив прогонов не входят в этап.

Первый рабочий сценарий — существующий локальный CSV и техническая SMA. Стратегии из mutations-bot не трогаем. Исправление всех финансовых метрик и фьючерсных инструментов — следующие этапы, но завершение позиций при Stop/конце истории необходимо реализовать уже здесь, а не заменять сменой статуса.

## Владение состоянием

- SessionManager принадлежит приложению Python, а не WebSocket-handler. Он хранит текущую сессию, конфигурацию, состояние и журнал событий.
- Один поток владеет NautilusEngine; операции с движком выполняются только в этом потоке. Все загрузка/инициализация/run/finalize/dispose находятся внутри общего try/finally.
- asyncio-цикл принимает команды, валидирует их и публикует события. Поток движка передаёт результаты через потокобезопасный канал; только менеджер обновляет публичное состояние и нумерует события.
- Управление потоком — отдельный объект с Condition: stop, желаемая пауза, скорость. Отключение подписчика этот объект не меняет. Никаких join или блокирующих threading-lock с await в WS-handler.
- У каждого подключённого клиента собственная очередь. Медленный клиент не блокирует движок: при переполнении соединение закрывается, клиент восстанавливается из нового снимка. Тихо терять события нельзя.

## Состояния

| Состояние | Значение | Разрешённые действия |
|---|---|---|
| idle | Сессии нет | start |
| loading | Загружаются/проверяются данные, создаётся движок | stop, speed |
| running | Идёт подача баров | pause, stop, speed |
| paused | Движок подтвердил остановку между барами | resume, stop, speed |
| stopping | Отменяется загрузка либо завершается исполнение | Повторный stop без дополнительных действий |
| completed | Все данные обработаны, позиции закрыты | start |
| stopped | Пользователь остановил тест, финализация завершена | start |
| failed | Ошибка исполнения/загрузки/финализации | start после завершения cleanup |

Переходы: idle/terminal → loading → running; running ↔ paused; loading/running/paused → stopping → stopped. Естественный конец: running → stopping → completed, причина `end_of_data`. Во время stopping итоговая причина уже определена: поздний Stop не превращает естественное завершение в пользовательскую остановку. Любая ошибка → failed после cleanup; сведения о невозможности закрыть позиции входят в ошибку.

Нельзя начать новый тест, пока предыдущий worker не закончил освобождение ресурсов. Start во время активной сессии возвращает SESSION_BUSY и не останавливает её. Ошибка валидации нового Start сохраняет предыдущий результат. После принятия корректного Start предыдущая сессия заменяется новой; ошибка последующей загрузки относится уже к новой сессии.

Повторные pause в paused и resume в running — успешный no-op. Две одинаковые ожидающие команды объединяются. Встречная команда до подтверждения перехода возвращает COMMAND_PENDING; UI не предлагает её до подтверждённого состояния. Stop имеет приоритет над паузой и скоростью. Неверное действие возвращает ошибку команды и не переводит весь тест в failed.

## Команды и подтверждения

Каждая команда содержит `protocol: 2`, уникальный `request_id` и `cmd`. Команды текущему тесту дополнительно содержат `run_id` — UUID, созданный сервером. Старый run_id возвращает STALE_RUN и никогда не воздействует на новый прогон.

```json
{"protocol":2,"request_id":"req-1","cmd":"start","config":{"csv_file":"BTCUSDT-1d.csv","strategy_name":"sma_crossover","strategy_params":{"trade_size":1},"speed":1}}
```

```json
{"protocol":2,"request_id":"req-2","cmd":"pause","run_id":"run-uuid"}
```

Команды этапа: start, pause, resume, stop, speed (`value`: целое 1–100), get_session. Существующие list_data/list_strategies/delete_data сохраняются; их ошибки не являются ошибками прогона.

Ответ отправляется только запросившему клиенту:

```json
{"protocol":2,"type":"command_result","request_id":"req-2","ok":true,"run_id":"run-uuid"}
```

```json
{"protocol":2,"type":"command_result","request_id":"req-3","ok":false,"error":{"code":"STALE_RUN","message":"Сессия уже сменилась"}}
```

`ok:true` означает принятие команды. Переход состояния подтверждает отдельное событие менеджера: pause считается выполненной только после paused. Start подтверждается после регистрации новой loading-сессии и до запуска worker; ready означает готовность данных и движка, а не заменяет статус.

Rust по-прежнему различает запись в сокет и ответ Python. Клиент ведёт pending-команды по request_id; таймаут ответа 5 с снимает ожидание, показывает «Результат команды неизвестен» и запрашивает get_session. Это не таймаут загрузки истории. Start автоматически не повторяется. При разрыве связи pending-команды также становятся неопределёнными; после реконнекта клиент получает актуальное состояние, не переотправляет команды.

Для защиты от повторной доставки менеджер хранит до 256 последних request_id с содержимым запроса и ответом. Повтор возвращает исходный ответ без повторного исполнения; тот же ID с другим запросом — REQUEST_ID_CONFLICT. После вытеснения записи гарантия дедупликации не действует, поэтому клиент никогда автоматически не повторяет изменяющие команды. request_id уникален на стороне клиента, новый осознанный клик — новый ID.

## События и снимок

Каждый запуск Python создаёт `server_id` (UUID). `seq` монотонно растёт в рамках server_id на каждом изменении сессии, включая смену run_id. Каталоги и ответы команд не участвуют в этой последовательности. Ревизия подключения Rust из этапа 1 остаётся отдельным внешним полем; она не заменяет seq/server_id.

```json
{"protocol":2,"type":"session_event","server_id":"server-uuid","run_id":"run-uuid","seq":42,"event":{"type":"state","status":"paused","speed":10,"reason":null}}
```

Содержимое `event`: state, ready, bar, progress, log, entry, exit, position_opened, position, position_closed, trade, result. Все события прогона проходят через менеджер. На этапе 2 существующие payload свечей/сделок адаптируются централизованно; переписывать их независимо в отдельных UI-компонентах нельзя. Нормализация финансовых полей и исправление маркеров относятся к отдельным задачам.

Снимок возвращается при подключении, по get_session и публикуется всем подписчикам при принятии нового Start:

```json
{
  "protocol":2,"type":"session_snapshot","server_id":"server-uuid","seq":42,
  "request_id":"req-sync",
  "session":{
    "run_id":"run-uuid","status":"paused","reason":null,
    "config":{},"speed":10,
    "progress":{"current":15,"total":73,"pct":20.54794520547945},
    "ready":{},"bars":[],"entries":[],"exits":[],
    "positions":[],"trades":[],"logs":[],"result":null,"error":null
  }
}
```

Для отсутствующей сессии `session:null`, UI показывает idle. `request_id` есть только у ответа на get_session. Пустые коллекции в примере обозначают форму; реальный снимок содержит всю накопленную историю. positions — текущие открытые позиции с обновляемыми значениями; position_closed удаляет позицию из этого списка. Все логи сохраняются в памяти, не обрезаются молча до последних 1000; UI может виртуализировать отображение. Большие снимки/постраничная доставка — последующая оптимизация с сохранением полного журнала.

Снимок соответствует точному seq: подписка, создание копии снимка и добавление его в очередь выполняются последовательно в asyncio-цикле без await между ними. Все последующие изменения идут после снимка в той же очереди клиента; отправляет сообщения единственная send-task. Использовать копию коллекций, а не ссылки на изменяемые массивы worker.

UI начинает применять события только после снимка. На том же server_id игнорирует сообщения с seq ≤ последнего принятого. Событие с seq > last_seq + 1 или неожиданным run_id инициирует get_session и временную остановку применения дельт; следующий актуальный snapshot восстанавливает состояние. Снимок может перескочить seq. Новый run_id принимается только через snapshot. При новой ревизии транспорта сначала нужна синхронизация; смена server_id допустима через snapshot текущего подключения и означает перезапуск Python.

Rust не отдаёт устаревший snapshot как источник истины: get_session пересылается живому Python. Открытие нового окна запрашивает снимок, даже если WS давно подключён. Разрыв соединения показывает disconnected, но не объявляет тест stopped/failed.

## Скорость, пауза, Stop

- Начальная скорость — 1 бар/с; диапазон 1–100, изменение допускается в loading/running/paused. Сервер публикует подтверждённую скорость; локальное состояние ползунка не является источником истины.
- Подача по монотонным часам, ожидание через Condition с прерыванием командами. Убрать get(timeout=0.1) после каждого бара. Скорость — целевой предел, а не обещание производительности на любой стратегии. После медленного бара не «догонять» историю бесконтрольной пачкой.
- Pause подтверждается между барами: уже выполняющийся бар можно закончить; после paused новые бары не приходят до resume. Stop будит paused и ожидание следующего бара.
- Во время загрузки Stop переводит в stopping; текущий сетевой запрос ограничен таймаутом, между страницами/фазами проверяется отмена. Поток насильно не убивается; новый Start недоступен до его завершения.
- Stop/конец данных: запрет новых входов стратегии, отмена активных заявок, закрытие позиций по последней доступной цене с комиссией; обработка финальных исполнений, обновление журнала и результата, dispose, терминальный статус. Не подавать следующий исторический бар ради закрытия и не вызывать стратегию повторно.
- Отмена до первого бара не создаёт фиктивных сделок. Ошибка закрытия не маскируется успешным completed/stopped: failed с описанием и фактическим состоянием позиций. Результат не подменять нулями.
- Прогресс current — число реально обработанных баров. Stop посреди истории не выставляет 100%; completed требует current == total. Во время загрузки total/pct могут быть null.

## Совместимость

Python, Rust-обёртки и frontend reducer обновляются одной согласованной поставкой. При protocol != 2 клиент показывает несовместимую версию и блокирует управление, а не пытается трактовать старые события как новые. Типы TypeScript, fixtures и адаптеры реализует Codex до передачи UI-задачи opencode.
